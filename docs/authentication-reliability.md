# Release 20 authentication audit

## Reproduced on release 19

The Firebase helper writes its initial OAuth state into the initiating browser tab. We started an actual Google handoff, stopped at the provider boundary, and opened the callback in a new tab on the same hostname. On both `rmtlaunch.fun` and `www.rmtlaunch.fun`, the helper rendered “Unable to process request due to missing initial state.” The original tab had the helper state key. Its value was never read. A plain desktop browser with working storage was sufficient. This reproduces the reported failure mode. The event that separated or removed state for the MoneyMomos owner is unknown.

Production GET and synthetic form POST checks confirmed that both domains serve their own helper without a cross-host redirect. Firebase's POST template received the supplied synthetic form data. Release 19 forwarded the terminal Firebase HTML untouched. The failure happened in that document, before RMT could receive an SDK error. Its mobile flow also launched from recognized embedded browsers after showing only a warning. A missing redirect result was treated like a normal signed-out visit.

## Release 20 behavior

- The authenticated identity, Firebase project, authorized hosts, HttpOnly session exchange, revocation checks and role policy continue to use release 19's implementation. Each supported production host uses its own matching callback from start to finish. There is no database migration.
- Account tests tab storage by writing, reading and removing a disposable key. It also checks local storage, cookie availability, framing and recognizable embedded-browser identifiers. An injected wallet extension alone never classifies a browser as embedded. Private mode alone never blocks sign-in. The SDK selects its available account persistence. A localStorage failure alone still permits Google when tab storage works.
- Healthy desktop browsers use a user-initiated popup. Healthy mobile browsers use a same-origin redirect. The SDK consumes the returning result once. RMT distinguishes an ordinary visit from an interrupted redirect. A back/forward-cache restoration with a pending redirect re-enters the app to resolve the outstanding attempt.
- The proxied handler offers a same-origin, parameter-free recovery link. Its observer notices Firebase's terminal error screen and returns to Account. A stalled handler retains a manual exit. Valid GET/POST callbacks continue to run Firebase's own initialization and validation. Google controls its own provider screens. Its OAuth policy restricts authorization in embedded user-agents. [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies) · [Firebase redirect guidance](https://firebase.google.com/docs/auth/web/redirect-best-practices)
- Recovery offers email/password, instructions for opening the regular browser and an allowlisted sign-in link with a manual copy fallback. A capable browser can explicitly try a fresh popup. Neither a failed callback nor reloading recovery starts Google again. The normal account refresh checks whether the browser retained its server session after an exchange.
- A 20-minute tab marker stores the attempt phase and an allowlisted destination. An expiring Secure, host-only navigation cookie can recover that destination in a fresh tab on the same host. Conflicting cross-tab destinations produce the neutral Account link. Copying a link shares only the public destination. Callback queries, OAuth state and private fields never enter this mechanism.
- Builder Studio keeps an account-scoped draft for up to one hour in the originating tab. An expired session leaves the form available while the member signs in again in a separate tab. Submission success or explicit sign-out clears the draft. Restricted storage permits in-memory recovery for the current page. A different browser or device cannot restore private draft fields from a link. Server authorization and revision checks still apply when resubmitting.
- Diagnostics use fixed local browser-console events under `[RMT auth]`, for example `redirect`, `no-result`, `handler_recovery` and `session-failed`. RMT adds no remote telemetry endpoint. For support, request the event label and whether the page returned to the original tab. Never request callback URLs, cookies, storage contents, account identifiers, email addresses or token values.

## Verification boundary

The isolated browser tests used the actual Firebase helper and client SDK. Successful controlled Google tests replaced account selection, consent and the provider exchange with a local fixture. The email tests used Firebase's Auth emulator. The server session tests exercised RMT's session handlers with isolated database records and fixture signing keys. These tests do not establish a sign-in with a real person's Google account. Desktop WebKit and mobile emulation do not certify native Safari or a physical phone. Recognizable X and wallet browser signatures can be simulated, but their real app-switch behavior requires actual devices.
