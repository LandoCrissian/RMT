# Release 24 wallet pilot decision

Baseline: published release 23, GitHub commit `3fbbbc39cee0ec55f724afb9099846b0501532b7`. No public rollout. The local connection preview, challenge verifier and Firebase provenance experiment are three independently tested pieces. There is no end-to-end production authentication path in this candidate.

## Security evidence

On November 24 the existing Firebase CLI session could read project `rmt-launch-auth-20261124`. Read-only IAM inventory returned one Firebase-managed Admin SDK service account, no workload identity pools, and IAM Service Account Credentials API state **DISABLED**. The public Sites Worker had site administration, notification, public URL and monitor settings, with no Google workload credential or signing-service binding. Local developer access cannot establish an identity for the deployed Worker.

In the Auth Emulator the Firebase Web SDK (13.4.0) signed in a disposable verified password member via a separately generated RS256 custom token for its exact UID. Initial and force-refreshed ID tokens carried the same subject, verified-email flag, custom sign-in provider, opaque link ID and generation; both had an authentication time. The private test key existed only in process memory. This verifies SDK behavior in the emulator. It does not exercise Google IAM, production token exchange, production refresh revocation or a physical wallet. The application candidate refuses custom or wallet-marked sessions at the common Firebase verifier, including cookies, account linking and privilege-bearing requests. Google and password continue through the release 23 path.

The isolated SQLite proof test uses viem's EIP-4361 message constructor and ERC-191 address recovery. It binds a five-minute nonce and exact message to purpose, browser digest, chain, address and linking UID, checks original-provider freshness, rejects unknown code, and consumes a challenge and applies the mapping in a synchronous transaction. A new random link identity is assigned on relink; old links fail session revalidation. The injected code reader and member/protection flags are test dependencies. A production verifier must obtain them exclusively from authoritative services, recheck current roles/monitor restrictions on **every** wallet session and deny on uncertainty. The preview only requests account connectivity. It does not issue Firebase sessions, sign messages or mutate mappings.

Three dedicated scenarios cover valid linking/login, competing verification, conflicting UID, unlink/relink, expiry, signature mismatch, network and purpose mismatch, changed browser, protected fixture rejection, unsupported code and rate limits. The application suite additionally tests rejecting custom-token sessions in each existing auth entry point. Mobile Chromium, desktop Chromium and mobile WebKit were exercised with injected provider fixtures, cancellation, disconnect, account change, network mismatch and layout checks. Real MetaMask iOS/Android, Google reauthentication for linking, ERC-1271 authorization and revocation, live signer exchange, and the protected owner/administrator/monitor matrix on a fully integrated pilot remain outstanding.

## Usage and architecture

This run used an isolated Auth Emulator and local database. Cloud inspection used three read-only Google inventory calls (service accounts, workload pools, and API state). There were zero cloud signing requests, paid RPC calls, or wallet transactions. The isolated challenge verifier enforces up to eight issues and twelve verification attempts per browser per five minutes, plus global hourly caps of 80 issues, 100 verification attempts and 40 code-verification operations. The local counters reset with the process. These are fixture budgets, not measured production headroom. A public pilot needs persistent atomic D1 budgets before expensive RPC, signer and Firebase calls, cleanup/retention, and measured daily caps for the selected infrastructure. WalletConnect is deferred; the injected provider path requires no relay subscription.

## Required infrastructure and release sequence

1. Establish an authenticated, **isolated** workload-to-signer path and confirm its identity model. Prefer a Google-hosted verification/signing broker or a verified OIDC workload exchange with short-lived credentials. Use a dedicated signer without Firebase administrative roles. Grant the calling workload only `iam.serviceAccounts.signBlob` on that signer if using IAM remote signing. Enable `iamcredentials.googleapis.com` in the chosen test project for this path. Never give the Worker an arbitrary-signing endpoint, developer OAuth credential or Admin SDK private key. A separate restricted operation must check an existing UID and its provider/verified status, and support refresh-token revocation. An ordinary email lookup cannot authorize a link. Measure quota and review any billable infrastructure before provisioning.
2. Verify real token exchange and forced refresh for a pre-existing ordinary test UID, stale/removed links, deleted users and remote revocation. Then wire the pilot to Account settings and fully authorized Control Center controls. Fresh original-provider authentication, linked generation and canonical Firebase/legacy UID must be checked server-side, including role changes and alternate entry points. Do not issue a token for a deleted user: Firebase custom sign-in can create an absent account.
3. Introduce only additive, initially empty D1 tables for links, generations, short-lived challenges and rate counters, plus a default-disabled control. No data migration or backfill is required on release 23. Apply first to isolated storage. Exercise the emergency disable switch, restricted aggregate diagnostics, duplicate prevention and provider recovery before any production migration. Keep project claims independent.
4. Complete real-device iOS/Android tests on an isolated HTTPS audience. Verify actual session recovery and price/quotas, then request pilot approval. Roll back an isolated experiment by stopping the preview/emulator and discarding its temporary data. For a later deployed pilot, disable new and existing wallet-origin sessions first, revoke affected Firebase refresh tokens, preserve primary-provider access and audit evidence, then restore the verified earlier worker. Retain additive tables until recovery is verified.
