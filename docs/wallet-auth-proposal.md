# Optional wallet sign-in for RMT

**Release 20 design decision, November 24, 2026.** Start with an isolated pilot for ordinary members who already have a verified Firebase account. A member explicitly links a wallet once, then can sign in with it. Google and email/password remain available for recovery. Wallet-only registration needs a later design for verified email, duplicate accounts and recovery. This release adds no wallet code, account mappings or subscriptions.

## Sign-in and account linking

1. The same-origin Worker issues a five-minute challenge on an explicit action. Generate at least 128 random bits for an alphanumeric nonce. Store a unique nonce digest, normalized account, chain ID, purpose, issue/expiry times, exact message hash and a digest of a short-lived HttpOnly, Secure, SameSite browser-binding cookie in D1. Bind a link operation to the current canonical RMT account and its fresh Firebase session. Rate-limit issuance and verification, cap request sizes and expire old rows.
2. Generate a version 1 Sign-In with Ethereum (SIWE) message on the server. For production pin the authority to `rmtlaunch.fun` and the URI to an exact HTTPS endpoint on that origin. Use separate audiences for isolated previews. Show the user the purpose, address, network and expiry before requesting `personal_sign`. Request **one message signature**. The flow requires zero gas, transactions and token approvals. Seed phrases and private keys stay in the user's wallet. [SIWE](https://eips.ethereum.org/EIPS/eip-4361)
3. On return, require the same browser binding, same-origin request and existing CSRF controls. Parse and match the exact original message, purpose, domain, URI, address, chain, nonce, dates and signature. Recover an externally owned account using ERC-191. For a deployed smart wallet, verify ERC-1271 against an allowlisted RPC for that chain, requiring the standard success value. Reject RPC uncertainty, unsupported counterfactual wallets and invalid signatures. Invalidate affected smart-wallet sessions or require a fresh proof when contract authorization changes. [Signature standard for contract wallets](https://eips.ethereum.org/EIPS/eip-1271)
4. Use one conditional database operation/transaction to consume a valid, unexpired, unused challenge and apply any wallet link. Enforce uniqueness on normalized chain and address. A second request loses even when two requests finish verification simultaneously. For login, resolve only an existing enabled link. For linking, require the verified account's original Google/password sign-in within five minutes and the independent wallet signature. Resolve legacy-linked canonical IDs and reject protected owner, administrator and Dot identities at linkage **and** login. Never accept an email or user ID supplied by the wallet as proof. Decline conflicts and route disputed links to manual recovery.
5. Exchange a successful single-use proof for a Firebase custom token for the exact linked Firebase UID. Carry an opaque wallet-link ID and generation in a server-issued session claim. A signing service scoped to the dedicated Firebase project would be necessary. Evaluate a short-lived IAM signing integration for the existing Worker before authorizing the pilot. The browser would exchange that token with Firebase and use the existing RMT ID-token/session path, account revocation checks, verified-email gates and role checks. Treat the custom token as a credential, return it only over TLS with `no-store`, and verify end-to-end that Firebase retains the member's verified email and auth time. Keep privileged and monitor routes closed to wallet-originated sessions even if a member's role later changes. [Firebase custom tokens](https://firebase.google.com/docs/auth/admin/create-custom-tokens)
6. Offer unlinking via fresh original-provider reauthentication. Retain a working recovery method, disable that generation immediately, revoke the user's Firebase refresh tokens and clear RMT's local session. Tell the member that Firebase revocation signs other sessions out as they revalidate. Re-check the active mapping on wallet-authenticated requests so previously issued tokens cannot keep using a removed link. Verify the wallet-link generation and authentication method survive refresh on the real SDK. Deny a custom-token session with missing provenance. Give the member a private security history. Restrict stored wallet mappings to the identity service and expose only aggregate outcomes in diagnostics. Logs exclude addresses, QR pairing URIs, signatures, nonces, Firebase tokens and email addresses.

## Project ownership stays in the review queue

For a contract-backed claim, request a **separate** short-lived, one-use signature naming the RMT project, claim ID, network and collection contract. Establish the canonical contract independently through an existing approved project source. Use a server-selected RPC, verify its chain ID and deployed code, and inspect the verified contract's actual authority model. Read the current collection-level `owner()` or a verified role that controls relevant administration. For proxies, follow the verified implementation and distinguish upgrade authority from project management. For multisigs, require the controlling contract's valid signature or independently verified threshold authorization. Record the block number and hash, chain, contract, authority checked and review time. Recheck at approval against a sufficiently confirmed block. An unavailable RPC, ambiguous delegated role, renounced contract, or change of control leads to manual review. [OpenZeppelin access control](https://docs.openzeppelin.com/contracts/5.x/access-control) · [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271)

A mint receipt, token balance or `ownerOf(tokenId)` establishes token-level activity or possession. It gives no project-management authority. Contract deployment history alone also cannot establish current authority. Reviewers still decide who may represent the project, including when an agency runs its contracts. Projects without contracts keep the existing manual evidence path using a challenge on an approved official domain or profile and the existing reviewer decision and audit trail. [ERC-721](https://eips.ethereum.org/EIPS/eip-721)

## Cost and release gates

| Item | Incremental cost and limits |
| --- | --- |
| Injected signing | Zero user gas and no wallet relay subscription. Budget existing Worker requests, D1 challenge issuance/consumption, Firebase authentication and IAM signing capacity. Each completed login needs at least two challenge operations and a Firebase exchange. Measure actual quota headroom before offering a public pilot. |
| WalletConnect | Reown lists Starter at **$0**, one project and a usage cutoff. Its pricing distinguishes self-custodial connection limits from the 500 monthly active users for its hosted authentication/embedded-wallet features. Confirm how it meters RMT's proposed transport-only use, its data retention and origin restrictions before enabling it. Reown lists Pro at $89/month or $890/year. A paid tier would require owner approval. [Reown pricing](https://reown.com/pricing) |
| Contract verification | Read-only RPC has zero user gas but consumes provider quota. Robinhood's public RPCs are rate limited and intended for development. Robinhood lists production providers including Alchemy. Alchemy lists 30 million monthly compute units on its free tier, shared across the account. Measure chain-specific read costs, set application limits, and fall back to established sign-in/manual review on exhaustion. [Robinhood endpoints](https://docs.robinhood.com/chain/connecting/) · [Alchemy free-tier limits](https://support.alchemy.com/articles/5827006872-what-is-included-in-the-free-tier) |

Before production, verify linking, unlinking, recovery, Firebase revocation, protected-role denial, expiry, replay rejection under concurrent requests, network mismatch, RPC failure and multisig verification in isolation. Test cancellation, backgrounding and return on physical phones with real wallets. Measure usage at expected peak volume and confirm an enforceable free-plan cutoff. Introduce the optional method behind a switch that can disable new wallet sessions while ordinary Firebase authentication and review continue. No devices or wallets have been certified by this design assessment.
