# Recovery capacity release

## Release decision

Hold the originally approved `0d2eee1057eb3b72f8e2a757eefc0261f135803a`. It allowed activation for up to one hour, gave the same window access to database and artwork export, and returned only a threshold flag. Its diff against Release 30 had five new files and no migrations or dependency changes. Sites version 33 still has the Release 30 archive, commit `66266ec91a5cb798332f35cfc9425b5c15e9a336` and deployment `appgdep_6b065dc63ad0819198753180c7cf2057`.

## Revised behavior

The replacement starts directly from Release 30. The route operates only on fixed aggregate SQL and schema table names. Database rows, artwork functions, and Firebase account exports are absent from the route. Missing or expired server configuration returns a non-cacheable 404. A start and end are mandatory and their difference is limited to ten minutes. A far-future expiration cannot become valid as it approaches without the matching bounded start. Set the dedicated immutable Firebase owner UID and confirm it matches one configured site-owner identity. Obtain fresh normal Firebase sign-in on the canonical site, then make a same-origin POST with a single `capacity` action. The existing verifier checks RS256, the Firebase issuer and audience, issue/expiry times, and the account lookup checks disabled/deleted/revoked status. The route checks verified email, expected sign-in provider and a five-minute authentication age. No observability code receives sensitive request fields, and the route catches errors without logging or returning provider diagnostics. Provider-wide log capture rules were not inspected.

The aggregate response contains exact per-table row counts, total rows, largest table, tables at or above 80% of the 2,000-row limit, tables over it, and database byte size when D1 supplies it. It indicates presence of SQLite sequences, recognized migration ledger tables and whether the expected application table inventory matches. Ledger presence does not certify what individual migrations ran. Database page size includes indexes and free pages and is not an estimate of serialized records. The 12 MiB serialization limit is reported unverified. Query latency and read consumption depend on production table sizes and remain unmeasured.

## Approved deployment and rollback sequence

After a new authorization, record the current Sites version and public smoke checks. Deploy with the recovery window absent. Confirm the 24 projects, spotlight order, public details/search, normal sign-in, administrator boundary, and non-cacheable 404. Inspect deployment metadata and error results. Set the server window for the shortest time practical, with the exact Firebase UID kept in owner settings. Call the same-origin aggregate action once. Clear activation bindings immediately and verify the response is 404 again. Capture public smoke probes and existing metadata after closure. On acceptance failure clear the window and redeploy the verified version 33 archive. Application rollback never needs a production D1 rewind.

## Isolated Recovery Center design

Add an owner-only screen with backup age, last completed backup, last verified restore, measured recovery point and elapsed recovery time, integrity, destination health, retention due dates, capacity warnings and an audit history. Keep aggregate health receipts separate from encrypted archives. The owner-held runner signs a bounded receipt containing an archive identifier, timestamps, counts, status and an allowlisted failure category. Never accept archive links with credentials, payloads, raw exceptions, keys or arbitrary metadata in receipts. Label rehearsal, backup and verified restore independently.

Use a freshly authenticated owner action for retention changes, archive retrieval and the emergency disable switch. Route downloads to the independent owner-controlled encrypted storage through its restricted access mechanism. The site stores no decryption material. The emergency switch revokes active windows and suspends scheduling. A separate restricted identity may read only summarized health and acknowledge incidents. Dot alerts on failure, excessive age, integrity mismatch, missed drill or newly crossed capacity limits. Deduplicate delivery per incident and send a recovery notice when it clears. Suppress repeating healthy notifications. The dashboard and scheduler remain isolated design work.
