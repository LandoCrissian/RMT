# Scalable independent recovery

## Capture selection

Use Cloudflare's supported full D1 export if an authorized operator can access the underlying database. Cloudflare documents that the export blocks other database requests and cannot export databases containing virtual tables. Establish the actual plan and intervention window before using this path. Restore the exported SQL into an isolated SQLite or D1 target with its own credentials and network policy. D1 Time Travel overwrites the named database and cannot create an isolated clone. Neither provider access nor a production write pause has been approved in this release. [D1 export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) · [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

When only the application binding is available, a bounded D1 batch can serve as one transaction under the documented D1 batch guarantee. The earlier isolated fixture observed consistent reads during overlapping writes. D1 sessions give sequential consistency across queries. Keeping a bookmark does not freeze a snapshot across pages. Separate page calls need a frozen source, a verified versioned journal covering every write and deletion, or a measured write pause covering all writers. Existing plaintext paging with independent transactions cannot establish completeness. A versioned journal would require schema and write-path changes plus an incremental recovery proof, so it is an independent engineering decision. [D1 batch and sessions](https://developers.cloudflare.com/d1/worker-api/d1-database/)

Once a consistent source is available, stream by primary key or by ordered archive offset with a byte ceiling and backpressure. On large values stream an entry separately or reject it with a recorded error. Encrypt independently resumable chunks using a mature authenticated format. Bind snapshot ID, dataset, sequence number and version into authenticated metadata. A durable receipt records each committed chunk and verified retry progress. Keep the final encrypted and authenticated manifest separate from partial work, and mark complete only after confirming expected tables, migration history, count totals, checksums, final chunk indexes and source timestamps. Bind restore to a new storage target and verify integrity, keys, indices, foreign keys, media hashes, owner-role preservation and representative authentication before considering any cutover.

R2 can traverse a paged inventory and resume per object, checking ETag, size and SHA-256 and preserving HTTP/custom metadata. Reconcile all database references against immutable object versions and record any missing object. Inventory matching is useful for detecting changes and does not provide atomic coordination with Firebase or D1. Capture Firebase UIDs and linked providers separately using Firebase Auth export, keep hash parameters under separate owner custody, and test isolated provider restoration. A product-wide cutoff needs a coordinated quiescent interval or application-level cross-store commit records that establish which versions belong to it. Record the separate capture windows and their skew until that work is available. [R2 Worker API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) · [Firebase auth export](https://firebase.google.com/docs/cli/auth)

Keep owner-held keys in an independent location with a second controlled recovery copy. Test decrypting a sampled archive on a clean machine and compare it to its manifest. Keep rotating encrypted weekly and recent generations based on measured storage availability. Scrub encrypted archives using authenticated verification and preserve the prior valid generation when a new run fails. Propose initial operational targets of a 24-hour recovery point and a four-hour recovery time, subject to a full-volume end-to-end drill. Measure archive data age at simulated incident time and elapsed time from starting recovery to validated availability. Local copy time is only one component.

## Synthetic scale observations

The local test copied independent SQLite fixtures, committed a later row to the source and scanned the immutable copy by indexed ID in pages of 1,000. Copy and scan are local laptop timings. JSONL sizes include each row's ID, payload and delimiters with the specified synthetic widths. They have no production data, network transfer, encryption, independent restoration, or real indexes beyond the primary key.

| Scenario | Rows | Payload bytes per row | JSONL MiB | Largest page KiB | Local copy / scan seconds |
|---|---:|---:|---:|---:|---:|
| Listings | 5,000 | 768 | 3.78 | 774 | 0.055 / 0.042 |
| Members | 10,000 | 256 | 2.68 | 274 | 0.049 / 0.068 |
| Members | 100,000 | 256 | 26.88 | 275 | 0.424 / 0.539 |
| Activity | 1,000,000 | 128 | 147.71 | 151 | 1.897 / 5.038 |
| Notifications | 1,000,000 | 384 | 391.85 | 401 | 4.680 / 6.340 |

Every scenario exceeds 2,000 rows when represented by one table. The 100,000-member and both million-row cases exceed 12 MiB before combining datasets. The separate activity and notification SQLite files totaled 552 MB before realistic secondary indexes. That would exceed Cloudflare's documented 500 MB per-database Free limit if stored together at those illustrative widths. Published D1 limits also include 30 seconds per SQL query and 50 MB per query result. Workers have 128 MB memory per isolate, so application object creation and serialization may exhaust memory below the body size. Managed Sites entitlements and deployment limits remain unconfirmed. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

At a hypothetical 512 KiB per original artwork, 10,000 objects require about 4.88 GiB and 100,000 about 48.83 GiB. Restore bandwidth, verified retry cost, retention copies and owner storage would dominate the metadata volume. Preserve object keys in encrypted manifests and use small metadata batches with streaming retrieval. These fixtures are capacity scenarios and do not forecast adoption.

## Separate workstreams

The earlier 5,000-project directory simulation needed 16.8 seconds to become ready. Backend catalog paging alone still sent the full catalog. Server-render a bounded first page, push search and category filtering into a stable indexed server query and fetch subsequent pages without hydrating the entire project list. Use the original synthetic datasets and repeat Chromium/WebKit measurements before a readiness claim. The reviewed bulk/audit and Dot suppression code stays on the audit branch.
